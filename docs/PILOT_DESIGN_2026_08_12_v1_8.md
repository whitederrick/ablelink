# Able-Link 직무지도원 문서 파일럿 설계 v1.8

> 구현 기준 문서
>
> 이 문서는 `WORKER_DOCUMENT_POC` 파일럿만 다룬다.  
> 급여·근로계약·연차·`AGENCY_FULL_FLOW`·정식 운영 정책은 범위 밖이다.  
> 이전 `PILOT_DESIGN_2026_08_12_v1_7.md`는 검토 이력으로만 보존하며 구현 기준으로 사용하지 않는다.

## 1. 목적

시스템 운영자가 파일럿 환경을 미리 설정하고, 직무지도원이 일반 사용자 화면에서 다음 흐름을 실제로 수행할 수 있는지 검증한다.

1. 로그인
2. 근태·일지 작성
3. 직무지도원 서명
4. 사업체 담당자 대면 서명
5. PDF 미리보기
6. PDF 로컬 다운로드

파일럿의 목적은 위 문서 사용 흐름을 확인하는 것이다. 정식 운영 전체를 검증하거나 급여·계약 정책을 결정하는 것이 아니다.

## 2. 참여자와 역할

### 2.1 시스템 운영자

별도 `파일럿 관리` 메뉴에서 환경 전체를 설정한다.

- 파일럿 기간과 실제 위탁기관 지정
- 사업체 등록 또는 기존 사업체 선택
- 훈련생 등록
- 직무지도원 배정
- 직무지도원과 담당 훈련생 연결
- 직무지도원 초대
- 위탁기관 담당자 표시명 선택 입력
- 파일럿 근무일 확인·정정
- 회차 종료와 데이터 폐기

### 2.2 직무지도원

초대를 받아 로그인하고 기존 직무지도원 화면을 그대로 사용한다. 사업체·훈련생·배정을 직접 등록하거나 관리하지 않는다.

### 2.3 위탁기관과 담당자

- 실제 위탁기관을 회차에 반드시 지정한다.
- 시스템 운영자와 직무지도원은 어느 위탁기관인지 알고 있다.
- 위탁기관 담당자는 파일럿에 참여하지 않으며 계정도 만들지 않는다.
- 담당자 개인 이름만 모를 수 있다.
- 운영자가 이름을 알면 입력할 수 있고, 모르면 PDF에 수기 입력 공간을 둔다.

### 2.4 사업체 담당자

기존 인퍼슨 서명 흐름으로 문서에 서명한다. 위탁기관 담당자와 혼동하지 않는다.

## 3. 범위

### 3.1 포함

- `WORKER_DOCUMENT_POC` 회차 생성·셋업·종료
- 운영자 발급 직무지도원 초대
- 기존 Worker와 신규 Worker 셋업
- 사업체·훈련생·배정·재적·담당 관계 설정
- 근태·일지 작성
- 직무지도원 서명과 사업체 담당자 대면 서명
- PDF 미리보기와 로컬 다운로드
- 위탁기관 담당자 이름 인쇄 또는 수기 공란
- 파일럿 데이터 격리와 종료 후 폐기

### 3.2 제외

- 급여 계산, 급여 기준, 급여 소급 검증
- 근로계약과 연차
- `AGENCY_FULL_FLOW`
- 위탁기관 담당자 계정·승인·전자서명
- 공단 제출·발송
- PDF·ZIP·문서 링크의 이메일·알림톡·webhook 전송
- 과거 운영 데이터의 divergence 조사
- 기존 문서·급여의 소급 재계산
- 출근부 1:1·1:多 정책 변경
- 불연속 담당 기간의 정식 문서화 정책

범위 밖에서 발견되는 문제는 이 파일럿의 착수 조건으로 편입하지 않고 별도 백로그에 기록한다.

## 4. 파일럿 회차

파일럿 여부를 기관이나 기간만으로 추론하지 않는다. 같은 기관이 정상 운영을 병행할 수 있으므로 회차 ID로 명시적으로 구분한다.

```text
PilotSession
- id
- agencyId                 실제 위탁기관
- startDate / endDate      파일럿 기간
- managerDisplayName?      담당자 표시명
- status                   DRAFT / READY / ACTIVE / ENDED / PURGED / CANCELLED
- createdByAdminId
- activatedAt? / endedAt? / purgedAt?
```

규칙:

- 두 유형을 병행하지 않는다. v1에서는 `WORKER_DOCUMENT_POC`만 존재한다.
- 한 시점에 `ACTIVE` 회차는 전역 1개다.
- `DRAFT`와 `READY`에서는 셋업 정보를 수정할 수 있다.
- `ACTIVE`에서는 `managerDisplayName`만 후입력·수정할 수 있다.
- `ENDED`, `PURGED`, `CANCELLED`에서는 모든 설정을 고정한다.
- `ACTIVE` 이후 기간·기관을 변경하거나 기간을 연장하지 않는다.

## 5. 운영자 셋업

### 5.1 기존 직무지도원

```text
회차 생성(DRAFT)
→ 사업체 선택/등록
→ 기존 Worker 선택
→ 배정 생성
→ 훈련생 등록
→ 재적 생성
→ 담당 관계 생성
→ 기존 계정 연결 초대
→ 설정 검증
→ READY
→ 초대 수락
→ ACTIVE
```

### 5.2 신규 직무지도원

계정이 없으므로 배정을 먼저 만들지 않는다. 회차 참여자에 배정 설정값을 저장한 뒤 초대 수락 트랜잭션에서 계정과 관계를 생성한다.

```text
회차 생성(DRAFT)
→ 사업체·훈련생·재적 설정
→ 참여자 배정 설정값 저장
→ 설정 검증
→ READY
→ 운영자 초대 발급
→ 초대 수락 트랜잭션
   (Worker + 배정 + 담당 관계 생성)
→ ACTIVE
```

초대 수락은 `READY`에서만 허용한다. 수락 완료 후 재요청은 같은 결과를 반환하도록 멱등 처리한다. `ACTIVE` 이후에는 참여자 추가·초대 발급·수락을 허용하지 않는다.

## 6. 문서 접근 관계

파일럿 전용 권한 우회는 만들지 않는다. 운영자가 설정한 기존 도메인 관계를 접근 근거로 사용한다.

훈련생 종속 문서의 접근 범위:

```text
요청 기간
∩ 파일럿 회차 기간
∩ 직무지도원 배정 기간
∩ 훈련생 재적 기간
∩ 직무지도원-훈련생 담당 기간
```

출근부는 직무지도원 본인의 문서이므로 훈련생 재적·담당 관계를 접근 조건으로 요구하지 않는다.

파일럿 v1에서는 담당 기간을 연속된 단일 구간으로만 설정한다. 불연속 담당 기간의 문서 생성 정책은 이번 범위에서 결정하지 않는다.

출근부의 1:1·1:多 표기는 기존 2026-06-18 확정 규칙인 `해당 날짜·현장의 재적 훈련생 수`를 그대로 사용한다. 담당 관계 도입을 이유로 이 규칙이나 급여 로직을 변경하지 않는다.

## 7. 파일럿 기능 권한

> **구현 결과로 갱신(2026-08-12, 5단계).** 아래 "당초 설계"는 새 회차 권한 게이트를 만드는 방식이었으나,
> 같은 목적을 **기존 경로 그대로** 달성할 수 있어 채택하지 않았다. 파일럿 때문에 기존 운영 코드를 고치지
> 않는 것이 우선한다.

### 7.1 채택안 — 기존 `worker.planType` 경로 사용 (코드 변경 0)

파일럿 참여자의 기능 권한은 **시스템 운영자가 직무지도원 개인에게 등급을 부여하는 기존 경로**로 통과시킨다.
`lib/planGuard.ts`의 판정 (1)번 갈래가 주석에 "초기 직무지도원 테스트/특례용"이라고 명시한 그 경로이며,
이번 파일럿이 정확히 그 용도다.

- 회차가 **새로 만든 Worker**에만 수락 트랜잭션에서 `planType = STANDARD`를 부여한다.
- **기존 Worker의 `planType`은 건드리지 않는다.** 폐기 시 원래 등급 복원을 놓치면 실제 직무지도원이
  값을 잃거나 공짜 유료 등급을 갖게 된다. 기존 Worker 참여자는 소속 기관이 이미 유료여야 참여할 수 있다.
- 결과적으로 `preview`·`generate`·`worker/signature`·`sign/[token]`·`inperson-sign`을 **한 줄도 고치지 않았다.**

### 7.2 수용한 절충 — STANDARD가 §1 흐름보다 넓다

`STANDARD` 등급은 §1 흐름에 필요한 세 기능 외에 다음도 함께 연다.

| 함께 열리는 기능 | 경로 |
|---|---|
| AI 음성 일지 (`AI_VOICE`) | `worker/ai/voice-to-log`, `worker/ai/batch-voice-to-log` |
| 출근부·일지 엑셀 내보내기 (`SHEET_EXPORT`) | `worker/export` |

`PAYROLL`·`CONTRACT_ONLINE` 등 PRO 전용 기능은 그대로 거부된다. 훈련생 리포트와 감사 패키지는
기관 축(`checkAgencyPlanAccess`) 판정이므로 `worker.planType`과 무관하다.

**결정(2026-08-12): 그대로 둔다.** 파일럿은 한정된 이해관계자만 사용하므로 통제 가능한 범위로 판단했다.
세 기능으로 좁히는 조이기는 파일럿 가동에 필요하지 않으므로 §14 백로그로 옮긴다.

### 7.3 (당초 설계 — 미채택, 이력)

회차 권한으로 `PDF_GENERATE`·`PDF_SIGN`·`SITE_MANAGER_SIGN` 세 기능만 허용하고, 파일럿 배정은 일반 플랜
판정으로 폴백하지 않는 fail-closed 게이트를 두려 했다. 이 방식은 문서·서명 라우트 전부에 판정 순서를
새로 넣어야 해서 기존 운영 경로를 건드린다. 7.1이 같은 결과를 코드 변경 없이 달성하므로 채택하지 않았다.

차단:

- 문서 데이터 webhook

직무지도원 화면에서는 `[위탁기관에 최종 제출]` 대신 `[파일럿 PDF 다운로드]`를 표시한다. 서버에서도 제출과 외부 전송을 차단한다.

직무지도원 계정 발급에 필요한 초대 SMS는 허용한다. 이는 문서 외부 전송이 아니다.

## 9. PDF 담당자 이름과 서명

`managerDisplayName`은 위탁기관 담당자 계정이나 전자서명이 아니라 PDF 표시용 문자열이다.

| 상태 | 위탁기관 담당자 이름란 | 위탁기관 담당자 서명란 |
|---|---|---|
| 표시명 입력 | 이름 인쇄 | 공란 |
| 표시명 미입력 | 고정 폭 수기 입력 공간 | 공란 |

문서 슬롯:

- 출근부·지원고용 훈련일지·적응지도 일지: `govAgent.name`
- 훈련생 종합평가·적응지도 종합평가: `agencyAgent.name`
- `companyManager`: 주입 금지. 기존 사업체 담당자 이름·대면 서명 흐름 유지

미리보기와 다운로드는 같은 담당자명 생성 함수를 사용해 동일하게 출력한다. 담당자 서명 공간은 이름 입력 여부와 관계없이 유지한다.

구현 메모(7단계):

- 슬롯 매핑은 기존 코드가 이미 위 표와 같아 변경하지 않았다.
- 수기 입력 공간은 렌더러에 새 그리기 코드를 넣지 않고 담당자 이름 자리에 고정 폭 밑줄을 넣어 처리한다. 전각 문자는 글꼴에 글리프가 없을 때 깨지므로 ASCII 밑줄만 사용한다.
- 표시명이 공백 문자로만 입력된 경우도 미입력과 같게 취급한다.
- 미리보기 경로와 다운로드 경로가 같은 함수 하나만 호출하도록 배선했다. 기존 비파일럿 동작은 그대로 둔다.

## 10. 근무일 처리

직무지도원이 실제로 근무한 날짜만 문서에 포함되어야 한다. 위탁기관 담당자가 없는 파일럿에서 기존 매니저 승인 경로에 의존하지 않도록 운영자 파일럿 관리 화면에서 회차 근무일을 확인·정정할 수 있게 한다.

- 오늘까지의 근무일: 생성·수정·삭제 가능
- 미래 근무일: 사전 생성하지 않음
- 일지가 연결된 근무일 삭제: 연관 데이터 확인 후 차단 또는 명시 처리
- 변경은 해당 파일럿 회차의 배정에만 적용

## 11. 데이터 격리와 폐기

운영 데이터에는 `pilotSessionId`를 명시적으로 기록한다. 기관+기간 또는 생성 시각으로 파일럿 데이터를 추론하지 않는다.

회차가 새로 만든 공유 자원은 `createdByPilotSessionId`로 구분한다.

정상 운영 자동화(월간 급여 DRAFT 생성 cron, 연차 자동 적립)는 파일럿 배정과 파일럿 생성 Worker를 제외한다. 이 필터는 자동화가 데이터를 생성하기 전에 적용한다.

삭제 가능:

- 파일럿 전용 초대
- 배정·재적·담당 관계
- 근태·일지
- 파일럿 PDF·서명 이미지·토큰
- 회차가 새로 만든 Site·Trainee 중 다른 정상 참조가 없는 자원

보존:

- 실제 Agency
- 기존 Worker
- 재사용한 Site·Trainee
- 감사 로그(자유 입력 PII만 비식별화)
- PilotSession과 참여 이력

파일럿에서 생성한 신규 Worker는 hard delete하지 않는다. 다른 정상 배정이 없으면 `PAUSED`로 전환하고 `sessionVersion`을 증가시켜 로그인을 차단한다.

폐기 완료 후 회차를 `PURGED`로 전환하고 `purgedAt`을 기록한다.

4. 운영자 파일럿 관리·셋업 화면 — 완료 (4-A 서버 / 4-B 화면 분할)
5. 파일럿 기능 권한 — 완료 (§7.1 채택으로 앱 코드 변경 없음)
6. 제출·외부 전송 차단 — 완료
7. PDF 담당자명·수기 공란·슬롯 매핑 — 완료 (선행 PDF 스윕 baseline 확보 후 착수)
8. 운영자 근무일 확인·정정 — 완료 (8-A 서버 / 8-B 화면 분할)
9. 폐기 기능과 테스트 — 완료

도메인 관계 마이그레이션과 파일럿 운영 메타데이터 마이그레이션은 분리한다.
운영 데이터베이스 마이그레이션 적용은 단계 완료와 분리해 별도 승인으로 진행한다.

## 13. 완료 조건

- 운영자가 실제 기관·사업체·훈련생·직무지도원을 회차에 설정할 수 있다.
- 신규·기존 직무지도원 모두 운영자 초대로 진입할 수 있다.
- 직무지도원이 일반 화면에서 근태·일지를 작성할 수 있다.
- 직무지도원과 사업체 담당자 서명이 정상 반영된다.
- 담당자 이름을 입력하면 PDF에 표시되고, 미입력하면 수기 공간이 나온다.
- 미리보기와 다운로드 결과의 담당자 이름이 일치한다.
- 최종 제출과 모든 문서 외부 전송이 서버에서 차단된다.
- 같은 기관의 정상 운영 데이터가 파일럿으로 오인되지 않는다.
- 종료 후 파일럿 데이터만 폐기되고 정상 자원은 보존된다.

## 14. 후속 백로그 — 이번 파일럿과 분리

다음 항목은 발견 여부와 관계없이 이번 설계·구현의 착수 게이트가 아니다.

- `AGENCY_FULL_FLOW`
- 급여·계약·연차 스코프
- 1:1·1:多 기준 변경 검토
- 운영 데이터 divergence 조사
- 과거 문서·급여의 소급 정책
- 불연속 담당 기간의 정식 문서화 방식
- 외부 전송 승인 기능
- 파일럿 권한을 §1 흐름 세 기능으로 좁히는 조이기 (§7.2 — 현재는 `STANDARD` 등급 그대로 사용)
- `/worker/docs` 인라인 PDF 미리보기 복구
  - 문서 제출 화면의 미리보기는 `<object data:application/pdf;base64,…>`인데 CSP `object-src 'none'`에 차단된다.
  - 실측(2026-08-12): 서버가 `[csp-report] {directive:"object-src", blocked:"data"}`를 수신한다. 사용자에게는 대체 문구만 보인다.
  - 파일럿과 무관한 기존 결함이며, 별도 화면 `/worker/docs/view`(iframe + 동일 출처 URL)는 정상이므로 §1의 PDF 미리보기는 충족한다.
- 시스템 운영자 모바일 요약 화면
  - `/admin/**`의 정식 업무는 데스크톱·노트북 사용을 전제로 유지한다.
  - 모바일에서는 핵심 현황·경고·처리 대기 건수를 보여주는 읽기 중심 요약 화면을 별도로 설계한다.
  - 복잡한 생성·수정·배정·문서 처리 기능은 모바일 요약 화면 범위에서 제외하고 데스크톱 사용을 안내한다.

## 15. 4-B 운영자 파일럿 화면 점검 기록 (2026-08-12)

점검 기준은 시스템 운영자 화면의 지원 기기 정책에 따라 **데스크톱·노트북**으로 한정한다. 360px에서 확인된 고정 사이드바와 본문 축소 문제는 4-B 결함이나 완료 차단 조건으로 분류하지 않고, 위 모바일 요약 화면 후속 과제로 이관한다.

데스크톱 시각 점검 결과:

- `/admin/pilots` 목록과 `/admin/pilots/[id]` 상세가 정상 렌더링된다.
- 파일럿 내비게이션, 목록 행, 단계별 카드, 비활성 상태와 선행조건 사유가 정상 노출된다.
- 위탁기관과 기간은 읽기 전용으로 표시된다.
- 주요 목록 셀은 한 줄을 유지하고 가로 오버플로 및 브라우저 콘솔 오류가 없다.
- `AddressMapPicker` 지도 모달과 Kakao 지도 로딩은 정상이다.

4-B 차단 이슈(주소 검색) — **해소 완료**:

- 당초 지적: 사업체의 "주소 검색" 버튼이 `/api/geo/search-address`를 호출하지 않고 기본 좌표의 `AddressMapPicker`만 열었다.
- 조치: 파일럿 전용 사업체 폼을 폐기하고 **기존 `/admin/sites/new` 화면을 재사용**한다(`?pilotSessionId=&returnTo=`).
  폼이 두 벌이 되면 한쪽에서 기능이 빠진다는 것이 이 결함의 실제 원인이었다.
- 재검증(데스크톱): 기관 읽기 전용 고정 → 주소 검색 → 결과 선택 → 좌표 자동 입력 → 지도 확인 → 등록 후 파일럿 상세 복귀까지 정상.

## 16. 5·6단계 시각 검증 기록 (2026-08-12)

직무지도원 문서 화면(`/worker/docs`)은 운영 화면이므로 비파일럿 무변경 확인을 완료 조건으로 둔다.

| 대상 | 버튼 | 안내 문구 |
|---|---|---|
| 비파일럿 배정 | `위탁기관에 최종 제출 (N개)` | 기존 문구 그대로 |
| 파일럿 배정 | `파일럿 PDF 생성 (N개)` | PDF 다운로드 안내로 대체 |

파일럿 계정으로 실제 동작까지 확인했다.

- `POST /api/worker/docs/generate` 200 — PDF 생성 성공
- `GET /api/worker/docs/preview` 200 — 출근부 PDF 렌더(성명·배치사업체명·지도기간 정상)
- 즉 §7.1의 `planType` 경로가 화면에서 실제로 성립한다.

## 17. 파일럿 코드 제거 가이드

회차 종료 후 파일럿 코드를 걷어내기 위한 기준이다. 모든 편집 지점에 `★[PILOT]` 주석을 달았으므로
`pilot` 또는 `[PILOT]` 검색으로 빠짐없이 회수할 수 있다.

### 17.1 삭제만 하면 되는 것

- `app/admin/pilots/**`, `app/api/admin/pilots/**`, `lib/pilot/**`
  - 8·9단계에서 추가한 `lib/pilot/workday.ts`·`lib/pilot/purge.ts`와 근무일·폐기 라우트도 전부 여기에 속한다.
- `scripts/verify-pilot-*.mts`, `scripts/smoke-pilot-*.mts`
  - `scripts/verify-pdf-sweep.mts`와 `scripts/pdf-sweep-baseline.json`은 **파일럿 전용이 아니다.**
    출근부 페이지 분할 회귀를 감시하는 일반 자산이므로 파일럿을 걷어낸 뒤에도 남긴다.
- 단, `lib/trainee/supervision.ts`와 `TraineeSupervision` 모델은 **파일럿이 아니라 D-1 운영 기능**이므로 남긴다.
  `lib/assignmentLock.ts`의 훈련생 락(NS=4)도 마찬가지다.

### 17.2 블록만 지우면 원복되는 기존 파일 (8개)

`★[PILOT]` ~ `★[PILOT] 끝` 사이와 해당 import만 제거한다. 비파일럿 동작은 판정이 추가되지 않았으므로 그대로다.

- `app/api/worker/docs/submit/route.ts`, `app/api/worker/docs/generate/route.ts`, `app/api/worker/docs/preview/route.ts`
- `app/api/admin/document-runs/send/route.ts`, `app/api/admin/sites/route.ts`
- `app/api/worker/invite/[id]/route.ts`, `app/api/worker/assignment/connect/route.ts`
- `app/api/worker/site/current/route.ts`, `app/admin/shell/components/AdminNav.tsx`
- `lib/assignmentLock.ts`도 파일럿 락 2개 함수와 상수만 제거하면 된다.

### 17.3 손으로 되돌려야 하는 화면 (2개)

- `app/worker/docs/page.tsx` — 파일럿 코드가 기존 줄을 치환한 유일한 화면이다. 원복할 문구 5곳을 파일 주석에 그대로 적어 두었다.
- `app/admin/sites/new/page.tsx` — `useSearchParams` 때문에 `Suspense` 래퍼와 내부 컴포넌트 분리라는 구조 변경이 있다. 원복 절차 4단계를 파일 상단 주석에 적어 두었다.

### 17.4 스키마

파일럿 테이블과 FK 컬럼은 모두 신규이거나 nullable이므로 삭제해도 기존 행에 영향이 없다. 남겨 두어도 무해하다.

되돌리기에 순서가 필요한 항목은 하나다. `worker_invites.created_by_manager_id`는 운영자 발급 초대를 위해
`NOT NULL`을 해제했으므로, 제약을 복구하려면 **운영자가 발급한 초대 행을 먼저 삭제**해야 한다(§11 폐기가 그 순서를 만든다).
함께 추가한 발급자 XOR CHECK 제약도 이때 제거한다.
